# 80 · 语料与评测

本篇回答：现有语料是什么样、有什么问题；新录制长什么样；有哪些场景；bench 输出什么；怎么和 scrcpy 比。

IDEA 的要求：从确定性的交互轨迹出发，一键录制，自动出全程体积 / 耗时 / 峰值，与 scrcpy 对比，再做消融。**这一套要最先做**，没有它启发式参数无法迭代。

## 1. 现有语料（`../corpus`）的结构

```
corpus/
  appi.js               # 采集脚本
  .appi/                # 工具链（Android SDK、node_modules）
  <设备>-<日期>/
    meta.jsonl          # 每步一行：app、seq、kind、是否有 xml、是否稳定，
                        #   以及 tap 的坐标与目标 / scroll 的 dx、dy、第几步，颜色数与熵
    baseline.json       # 仅 razr：旧编码器的基线与消融快照
    <包名>/NNNN.png     # 每步一张整屏截图
    <包名>/NNNN.xml     # 部分步骤有 uiautomator 的节点树
```

`kind` 有六种：launch、tap、back、recover、scroll_step、scroll_end。两台设备：razr（11 个 App）和 xiaomi（7 个 App）。

## 2. 对现有语料的建议

| 现状 | 影响 | 建议 |
|---|---|---|
| 是“步进快照”：没有时间戳，一次滚动只有几张中间帧 | 测不了稳定判定、预取、延迟。旧项目吃过亏：用固定帧间隔重放时，页面缓存的收益被藏了起来，换成接近真人的间隔才显现 | 新录制是带时间戳的连续帧 |
| 滚动步没有节点树；节点树是 uiautomator 的精简格式 | 本方案要用的信息缺失：能往哪个方向滚、窗口标题、属于哪个 display、是否可见、可编辑焦点、滚动事件 | 由 host 自己录全量节点树和 A11y 事件 |
| 测试采集脚本随机游走且混入桌面壁纸 | 换页多、滚动少，不可复现；旧测试脚本退回桌面导致 `back` 类占下行 **48.6%**（多数是多色桌面壁纸帧，正常会话不产生） | 换成按意图命名的确定性场景；旧语料里因测试脚本走出范围的帧打 `in_scope=false` 并从预算统计里剔除 |
| 旧测试脚本未及时把目标 App 拉回前台（标签错位） | 旧语料 451 个 dump 里 49 个（11%）非目标包，其中 30 个其实是前一步测试的另一个白名单 App 还留在前台（脚本问题而非真越界），真越界仅 19 个（4.2%） | 新录制由 host 自己驱动并每帧记实际栈顶包名，不再出现脚本标签错位 |
| 两台设备几何不同：razr 是物理屏截图（部分页面内容两侧有缩进），xiaomi 是虚拟屏 | 和生产路径（虚拟屏）不一致 | 一律在虚拟屏、生产几何下录；几何写进 manifest |
| 包名有设备替代（razr 上的日历用了 Google 版） | 跨设备对不齐 | manifest 记实际包名与版本；替代关系放配置 |
| 帧编号在一个设备目录里有重叠（看起来是两次采集合在一起）；`meta.jsonl` 有的行缺字段 | 脚本要写特例 | 每个场景一个目录，序号从 0 起；带 schema 版本号 |
| 每步一张整屏 PNG | 体积大，相邻帧大量重复 | 首帧完整 + 之后只存变化的行 |
| 工具链和数据在同一目录 | 备份、拷贝语料时带上一大堆无关文件 | 工具链挪到单独目录 |
| `baseline.json` 是旧编码器（整屏对上一帧）的数字 | 口径和新方案不同，不能直接比 | 只存档。新基线由 bench 生成 |

旧语料还能用来做什么：静帧上的图 / 文分类和 Palette 判定的回归集。滚动、缓存、延迟相关的结论不要从它得出。

## 3. 新录制格式

```
../corpus/trace/<设备>/<包名>/<场景>/<批次>/
  manifest.json   # schema 版本、设备与系统版本、虚拟屏宽高与密度、字体缩放、深浅色、
                  # 包名与版本、场景名与脚本 hash、host 版本、各项系统设置
  events.jsonl    # 一行一个事件，带 B 的单调时钟时间戳
  frames.bin      # 第一帧完整，之后只存变化的行段，无损
  frames.idx      # 帧号 → 偏移
  trees/NNNN.json # 全量节点树
```

`events.jsonl` 的事件类型：

| type | 内容 |
|---|---|
| `step` | 场景步骤：点哪个节点、滚多远、返回、输入什么文本 |
| `inject` | B 实际注入的原始事件（滚轮步、触摸点、按键） |
| `frame` | 帧号、当时的栈顶包名 |
| `a11y_event` | 事件类型、来源节点、滚动量等 |
| `a11y_tree` | 对应的 `trees/` 文件、窗口 |
| `stack` | 栈深、栈顶 Activity |
| `mark` | 场景脚本打的标记：步骤开始 / 结束、步骤名、`disconnect` / `reconnect` |

要点：

- **录制只记录 App 的行为：输入 → 画面 → A11y。不经过编码器和调度器。** 所以算法怎么改都不用重录。
- **录制器就是 host**（`--record <目录>`）。和生产同一条采集、A11y、注入路径，录到的就是线上会遇到的。
- 录制时场景脚本直接驱动 B 的真实滚动位置（滚轮步进）和点按，虚拟屏保持 1×。
- 节点树录全量：类名、resource-id、文本、描述、矩形、可滚动与方向、`CollectionInfo`（总项数）与 `CollectionItemInfo`（`rowIndex`，uiautomator 的 XML dump 会丢掉它）、可点击、可编辑、焦点、可见性、所属窗口与 display。
- 同一场景在同一设备上录两次，除了时间戳，帧内容应一致。不一致说明场景不确定（有动画、有网络内容），要修场景或换 App 页面。
- 超高虚拟屏另录一类：同一页在 1× 和加高下各录一次完整滚动，用来核对“加高帧拆出来的画布”等于“1× 滚动拼出来的画布”。

## 4. 场景

场景按意图命名，每个带一条**可以自动检查的性质**。

| 场景 | 步骤 | 性质 |
|---|---|---|
| `cold-open` | 打开 App，等稳定 | 画面正确；记首屏字节与耗时 |
| `scroll-down-up` | 主列表往下滚若干屏，再滚回顶 | 回程没有像素字节 |
| `enter-back` | 进子页 → 返回，重复三轮 | 第二轮起没有像素字节 |
| `reconnect` | 浏览几页 → 断开 → 重连 → 再走一遍 | 第二遍只有握手和 `Page` |
| `toggle` | 同一个开关来回点几次 | 第二次起只有引用，没有字面量 |
| `dialog` | 打开弹窗 → 关闭，重复 | 下层页面不重发；关闭后没有像素字节 |
| `long-list-steady` | 匀速滚一个长列表 | 白块指标 |
| `scrollbar-jump` | 跳到列表远处再跳回 | 画面最终正确；回到已见位置没有像素字节；远跳落零散段，滚回对齐后合并，长截屏坐标不错位 |
| `taps-in-place` | 计算器连续按键 | 按下高亮不进画布（结束后画布等于初始） |
| `image-heavy` | 新闻 / NewPipe 首屏并滚动 | 记图片层字节；文字区域逐像素一致 |
| `tab-switch` | NewPipe 切 tab 再切回 | 切回没有像素字节（M6 之前只记录，不要求） |
| `editor-type` | qpython 编辑器里输入一段文字 | 每次按键的下行很小；光标闪烁不进画布 |
| `off-whitelist` | 设置里点搜索 | 被拦截并返回 |
| `scroll-then-tap` | 滚到某个条目再点它 | 进入的是该条目对应的页面 |

每个白名单 App 至少有 `cold-open`、`enter-back`；有列表的再加 `scroll-down-up` 和 `scroll-then-tap`。

## 5. 场景 runner（`e2e/`，`appi.js` 的精简重写）

- 场景 = 一个 JS 文件，导出步骤数组。步骤原语：`open(pkg)`、`tap(选择器)`、`scrollBy(距离, 速度)`、`scrollTo(选择器)`、`back()`、`type(文本)`、`waitStable()`、`mark(名字)`、`disconnect()` / `reconnect()`。
- 选择器基于 host 给出的节点树（resource-id、文本），不写死坐标，所以换设备也能跑。
- `disconnect()` / `reconnect()` 在录制时只打标记；bench 在标记处模拟断线和重新握手。
- runner 通过 `adb forward` 连 host 的调试口（[60](60-host.md) §10）。**不经过 Appium server**：UiAutomation 只能有一个持有者，host 已经占用了。
- 一条命令录一个场景；一条命令录全部（每个 App × 适用的场景）。命令写进 README。

同一套场景还有第二种跑法（M1 之后）：**实跑**。runner 扮演 A，通过调试口发 wire 消息（`Tap`、`View`、`Back`…），走完整的编码、调度、解码链路，检查同样的性质。它用来验收真机上的整条链路；录制和 bench 用来迭代算法。

## 6. bench

两种模式：

| 模式 | 输入 | 能评什么 | 不能评什么 |
|---|---|---|---|
| **帧重放** | 录制的帧、节点树、步骤，按时间戳喂。模拟的 A 视口跟随 B 的真实滚动位置 | 识别、编码、页面缓存、Overlay、返回栈、握手对齐 | 预取（视口和采集头没有分开） |
| **页面模拟** | 每个页面的整页长图（由一次完整滚动录制拼出）+ 一条用户视口轨迹 | 预取与调度：模拟器按调度器的指令从长图裁出帧，并加上录制里量到的出帧延迟 | 会变化的页面 |

管线：帧 → rd 编码器 → 网络模型（带宽、往返延迟、抖动）→ rd 解码器 → A 的画布。全程用录制里的时间戳，不读墙钟，所以同一份录制、同一组参数，两次运行的输出应完全相同。

每个场景和汇总都输出：

- **主指标（用法加权速率与首屏预算）**：脚本化真实会话的**每分钟字节数（KB/min）**，并按五类交互拆解——**首访 / 回访 / 新滚 / 回滚 / 点击**（剔除 `in_scope=false` 越界帧）；首屏字节对照 300 KB/s × 300 ms ≈ **90 KB**（p90）预算线；
- 下行总字节；按层、按 Op 类型、按步骤（`mark`）分的字节；
- 每一步“输入 → A 的画面正确（首屏先出字）”的耗时分布；
- 码率峰值、发送队列峰值；
- 编码耗时、解码耗时；
- 白块指标（缺行面积 × 持续时间，相对视口面积和滚动时长归一）；
- 各机制省了多少（用真实的影子编码：把被省掉的矩形真的按字面量编一遍）；
- **离线真值打分与 oracle 上界**：
  - 用录制里已知的注入滚轮增量（`inject`）、A11y `scrollY / rowIndex` 和慢速拼出的长截屏作为离线真值，给位移检测器与图片分类器算误差（regret）；
  - 评估复杂编码特性前，先在语料上算 `oracle dedupe`（最优去重上界）与 `oracle static`（最强静态无损下界）；
  - 调参时留出 hold-out 设备/轨迹，防启发式过拟合；
- 正确性：每一步结束时，A 的画布在 B 当前帧覆盖的范围内与该帧一致（有损图片和模态页压暗的背景除外）；场景自带的性质是否成立。

报表落到 `bench/out/<日期>-<git 版本>/`（一份 JSON + 一份 markdown）。每个里程碑结束留一份，下一份与它对比。

## 7. 对照

| 对照 | 怎么做 | 说明什么 |
|---|---|---|
| 朴素基线 | 每帧整屏对上一帧求脏区，zstd | 本方案各机制的起点 |
| x264 | 同一批帧离线过 x264，码率封顶在同一档 | scrcpy 这类方案在同样带宽下的字节、到画面清晰的耗时、文字区域有多少像素和原图不同 |
| scrcpy 实机 | 同一个场景脚本在 `cmp-scp/` 上跑一遍，记流量和观感 | 旁证。两边不是同一批帧，只比量级 |

## 8. 消融

同一批录制，逐个关掉特性重跑，输出一张表：关掉之后下行字节变多少、编码耗时变多少。

要逐个评估的特性：位移 / 画布（本地滚动）、页面缓存（返回）、Overlay、行引用、跨页引用、无损精灵、有损图片、预取、超高虚拟屏，以及 [40](40-codec.md) §12 的候选项。

收益不明显、又增加复杂度的特性不进默认配置，并在报表里写明。

## 实现备注（M0）

- **人工录制优先**：`e2e/recorder.mjs` + `recorder.html`（本地服务直接落盘 `e2e/cases/<包名>.jsonl` 与截图，网页内可回放）、`e2e/run.mjs` 回放比对；格式与已知限制见 `e2e/README.md`。通用场景（`e2e/scenario.mjs`：`cold-open`、`scroll-down-up`、`enter-back`）排在它之后。
- **手势确定性**（实测，设置 App）：事件间隔短于一帧或每步位移过大时，同一轨迹两次回放结果不同（14ms/107px 差 5–7%）；重采样成 30ms 间隔、每步 ≤ 60px、终点停 60ms 再抬手后，3 次回放逐像素一致。录制时浏览器只收轨迹、松手后一次性注入，保证“录的就是回放的”。
- **语料录制器**（`Recorder.kt`，host 的 `rec_start` / `--record`）：`frames.bin` 每条 13 字节头（LE：seq u32、kind u8、rawLen u32、zLen u32）+ zlib 载荷；整帧每 120 帧一个关键帧，其余是变化行段 `[y0 u16 BE, n u16 BE, n 行 RGBA]`；`frames.idx` 每帧 16 字节（seq u32、t u32 ms、offset u64，LE）。树在 A11y 窗口状态 / 内容 / 滚动事件后去抖 250ms 取一棵。读取实现：`e2e/lib/trace.mjs`（已验证导出的帧与当时画面逐像素一致）、`bench/src/trace.rs`。
- **bench**（`bench/`）：`Encoder` trait + 朴素基线（行 hash 脏带 → zstd）、整数微秒网络模型、`report.json`（无墙钟，两次逐字节相同）+ `timing.json`（墙钟）+ `frames.csv`、x264 对照（ffmpeg，veryfast/zerolatency/threads=1）。M0 未区分回访 / 回滚；离线真值、oracle、消融、白块指标、页面模拟模式留给后续里程碑。
